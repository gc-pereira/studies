Apache Spark

Conceitos fundamentais, arquitetura, execução, tuning e debugging

Conceitos Fundamentais do Apache Spark

O Spark é um motor de processamento distribuído em memória, criado para superar as limitações do MapReduce. Em vez de gravar resultados intermediários em disco após cada etapa, o Spark mantém os dados em RAM entre as operações — o que pode ser 10 a 100× mais rápido para workloads iterativos. Abaixo estão os conceitos essenciais que todo engenheiro de dados precisa dominar.

Abstração de Dados
RDD — Resilient Distributed Dataset
A abstração mais baixa do Spark. Um RDD é uma coleção imutável e distribuída de objetos, particionada entre os nós do cluster. É "resiliente" porque o Spark sabe como recriá-lo automaticamente (via lineage) se uma partição for perdida. Embora ainda disponível, para a maioria dos casos use DataFrames ou Datasets, que oferecem otimizações automáticas via Catalyst.
Abstração de Dados
DataFrame & Dataset
Um DataFrame é um RDD organizado em colunas nomeadas com schema — similar a uma tabela SQL. Permite ao Catalyst Optimizer gerar planos de execução eficientes automaticamente. O Dataset (Scala/Java) adiciona tipagem estática. Em PySpark, o DataFrame é a API principal; oferece predicado pushdown, column pruning e otimizações que o RDD bruto não tem.
Modelo de Execução
Transformações vs Actions
Transformações (map, filter, join, groupBy) são lazy: constroem um plano de execução (DAG) mas não executam nada. Actions (count, collect, write, show) disparam a execução real. Essa separação permite ao Spark otimizar toda a sequência de operações antes de rodar — evitando processamento desnecessário. Nunca chame collect() em DataFrames grandes; traga apenas o necessário ao Driver.
Modelo de Execução
DAG — Directed Acyclic Graph
Ao receber uma action, o Spark constrói um DAG representando todas as transformações necessárias. O DAG Scheduler converte esse grafo em estágios (stages), separados por operações de shuffle. O DAG permite ao Spark retomar execuções parciais em caso de falha (fault tolerance) sem reprocessar tudo do zero.
Particionamento
Partições
Partições são as unidades de paralelismo do Spark — cada task processa exatamente uma partição. Muitas partições pequenas geram overhead de scheduling; poucas partições grandes deixam cores ociosos. O tamanho ideal é 128 MB a 512 MB por partição. Use repartition(n) para redistribuir com shuffle, e coalesce(n) para reduzir sem shuffle.
Otimização
Catalyst Optimizer
O Catalyst é o otimizador de queries do Spark SQL. Ele transforma sua query em um Logical Plan, depois em múltiplos Physical Plans, seleciona o mais eficiente por custo estimado e gera código bytecode via Whole-Stage CodeGen. Aplica automaticamente predicado pushdown (filtra antes de ler), column pruning (lê só as colunas necessárias) e constant folding.
Otimização · Spark 3+
AQE — Adaptive Query Execution
Enquanto o Catalyst otimiza antes da execução, o AQE otimiza em runtime, baseado em estatísticas reais coletadas durante o shuffle. Faz três coisas automaticamente: (1) coalescência de partições pequenas após shuffle, (2) conversão de Sort-Merge Join em Broadcast Join quando detecta tabela menor que o threshold, e (3) divisão de tasks skewed em sub-tasks. Habilite sempre com spark.sql.adaptive.enabled=true.
Memória
Modelo de Memória Unificado
Desde o Spark 1.6, a memória do executor é dividida em: Reserved Memory (~300 MB, sistema), User Memory (~40%, para estruturas Java/UDFs) e Spark Memory (~60% da heap, configurável via spark.memory.fraction). Dentro do Spark Memory, Execution (joins, sort, shuffle) e Storage (cache) compartilham o mesmo pool e tomam espaço um do outro conforme a demanda.
Tolerância a Falhas
Lineage & Fault Tolerance
O Spark não replica dados como o HDFS faz. Em vez disso, mantém o lineage — o grafo de transformações que gerou cada RDD/DataFrame. Se um executor falha e perde partições, o Spark recomputa apenas as partições perdidas reexecutando as transformações necessárias a partir da fonte original. Isso torna o Spark eficiente em memória e resiliente sem replicação excessiva.
Processamento
Lazy Evaluation
Transformações Spark são preguiçosas (lazy): ao encadear .filter().select().join(), nenhum byte de dados é processado. O Spark acumula o plano. Só quando uma action é chamada o DAG é enviado ao cluster para execução. Benefício: o Catalyst pode reordenar, combinar e eliminar operações desnecessárias antes de qualquer dado ser movido.
Distribuição
Shuffle
O shuffle é a redistribuição de dados entre partições via rede — necessário em operações como groupBy, join, repartition. É a operação mais cara do Spark: envolve serialização → escrita em disco → transferência de rede → leitura → desserialização. Minimize shuffles: use broadcast joins para tabelas pequenas, bucketing para joins frequentes, e AQE para coalescência automática.
Dados
Broadcast Variables
Variáveis broadcast enviam uma cópia read-only de um objeto a todos os executores uma única vez, evitando que seja serializado e reenviado junto com cada task. Ideal para tabelas de lookup pequenas, dicionários de configuração e modelos ML. Use spark.sparkContext.broadcast(dict) e acesse com .value. O Spark remove automaticamente ao fim do job, ou use .unpersist() explicitamente.
Dados
Accumulators
Accumulators são variáveis de escrita distribuída — cada executor só pode adicionar a eles; apenas o Driver pode ler. Úteis para contadores e somatórios durante a execução sem afetar o resultado principal. Exemplo: contar linhas com erro, registros nulos, ou eventos específicos durante um pipeline. Atenção: em tasks reexecutadas por falha, o acumulador pode ser incrementado mais de uma vez.
Leitura
Predicate Pushdown & Column Pruning
Predicate Pushdown: o Spark empurra filtros (.filter("year = 2024")) para o leitor de dados, que os aplica antes de carregar dados na memória — lendo apenas os row groups relevantes no Parquet. Column Pruning: ao fazer .select("col_a","col_b"), o Spark lê somente essas colunas do arquivo colunar. Juntos, podem reduzir o volume de I/O em >90%.
Performance
Bucketing
Bucketing pré-particiona e pré-ordena dados por uma coluna ao salvá-los (bucketBy(N, "user_id").sortBy("user_id")). Quando dois DataFrames são bucketizados com o mesmo número de buckets e chave, o Spark elimina completamente o shuffle em joins futuros entre eles. Ideal para tabelas grandes lidas repetidamente com a mesma chave de join. Requer Hive Metastore ou Glue Catalog.
APIs
UDFs vs Funções Nativas
UDFs (User Defined Functions) executam fora do Catalyst — o Spark não consegue otimizá-las, elas serializam/desserializam dados row-by-row e podem ser 10-100× mais lentas que funções nativas. Sempre prefira funções de pyspark.sql.functions (nativas, compiladas). Se precisar de UDF, prefira Pandas UDFs (vectorized) que operam sobre Arrow batches, muito mais eficientes que Python UDFs escalares.

Arquitetura Spark: Nós, Cores, Executores e Hierarquia de Execução

O Spark opera em um modelo mestre-trabalhador. O Driver é o cérebro: orquestra a execução, constrói o DAG e coordena os Executors, que são os músculos — processos JVM rodando nos Worker Nodes que realmente executam as tasks sobre os dados.

Como calcular executores (regra prática)

Para instâncias com 16 cores e 64 GB RAM: reserve 1 core + 1 GB para o sistema operacional e YARN. Restam 15 cores e 63 GB. Com executor-cores = 5, cabem 3 executores por nó. Cada executor fica com ~21 GB RAM. Ajuste executor-memory deixando ~7% para memoryOverhead.

# Exemplo: cluster 5 nós × 16 cores × 64 GB
--executor-cores   5
--executor-memory  19g
--num-executors    14   # (3 por nó × 5 nós) - 1 driver

Regras de ouro de particionamento

✓ Tamanho ideal de partição 128 MB a 512 MB por partição. Partições muito pequenas (<10 MB) geram overhead de scheduling; muito grandes causam OOM nos executors.
⚠ shuffle.partitions vs default.parallelism spark.sql.shuffle.partitions (padrão: 200) controla partições pós-shuffle no SQL. spark.default.parallelism controla RDDs. Com AQE ligado, o Spark ajusta o número de partições automaticamente em runtime.

Tungsten: Engine de Execução Física

Tungsten é o subsistema de execução física do Spark, introduzido no 1.4 e aprimorado continuamente. Seu objetivo é fazer o Spark se aproximar do limite físico do hardware — aproveitando ao máximo a CPU e a memória, em vez de desperdiçar ciclos com overhead de JVM e GC. Funciona em três frentes simultâneas:

GC, OOM: Debugging e Tuning

O Garbage Collector (GC) da JVM é responsável por liberar memória de objetos que não são mais referenciados. O problema é que o GC clássico (G1, CMS) para todos os threads do executor enquanto roda — as chamadas Stop-the-World pauses. Quando a heap fica quase cheia, o GC roda constantemente, consumindo mais CPU do que processando dados, até lançar OutOfMemoryError.

Parâmetros de Tuning de Memória e GC

# Heap do executor
spark.executor.memory         = 16g

# Off-heap: overhead nativo, Python, Arrow
spark.executor.memoryOverhead  = 2g

# Fração da heap dedicada ao Spark
spark.memory.fraction          = 0.6

# GC: G1 é melhor para heaps > 4 GB
spark.executor.extraJavaOptions =
  -XX:+UseG1GC
  -XX:InitiatingHeapOccupancyPercent=35
  -XX:G1HeapRegionSize=16m
  -verbose:gc -XX:+PrintGCDetails

Como debugar GC no Spark UI

Spark UI → Executors → coluna "GC Time" Se GC Time > 10% do Task Time, há problema sério. Se > 30%, os executores estão a maior parte do tempo parados em GC — aumente memória ou reduza cores por executor.
⚠ Erros comuns de OOM GC overhead limit exceeded → GC > 98% CPU
ExecutorLostFailure → executor morreu por OOM
Container killed by YARN → ultrapassou limite YARN (aumente memoryOverhead)

Shuffle, Skew e Salting

O shuffle redistribui dados entre partições via rede — é necessário em operações como groupBy, join e repartition. Envolve serialização → escrita em disco → transferência de rede → leitura → desserialização. É a operação mais cara do Spark e a principal fonte de problemas de performance.

O skew ocorre quando certas chaves concentram muito mais dados que outras (ex: country = 'BR' tem 80% das linhas). O resultado são straggler tasks — algumas tasks demoram 10× mais que outras — bloqueando o estágio inteiro até a última task terminar.

Debugging de Skew no Spark UI

Stage Details → Task Metrics → ordenar por Duration Se P95 > 5× mediana das tasks, é skew. Verifique também a coluna "Shuffle Read Size" — uma task com 10× mais dados que as outras confirma skew de dados, não de processamento.

Tuning: AQE (Spark 3+)

# Habilita Adaptive Query Execution
spark.sql.adaptive.enabled              = true

# Detecta e divide tasks com skew
spark.sql.adaptive.skewJoin.enabled     = true

# Coalesca partições pequenas após shuffle
spark.sql.adaptive.coalescePartitions
  .enabled                              = true

Salting Manual — Solução Clássica para Skew de Join

# Salting distribui chaves skewed adicionando sufixo aleatório
import pyspark.sql.functions as F

n = 50  # salt factor — ajuste conforme o grau de skew

# Tabela GRANDE: adiciona salt aleatório (0 a n-1)
df_large = df_large \
    .withColumn("salt", (F.rand() * n).cast("int")) \
    .withColumn("key_s", F.concat("key", F.lit("_"), "salt"))

# Tabela PEQUENA: explode com TODOS os valores de salt
df_small = df_small \
    .withColumn("salt", F.explode(F.array([F.lit(i) for i in range(n)]))) \
    .withColumn("key_s", F.concat("key", F.lit("_"), "salt"))

result = df_large.join(df_small, "key_s").drop("salt", "key_s")

Tipos de Join no Spark

O Spark escolhe automaticamente a estratégia de join com base no tamanho estimado das tabelas e nas configurações. Entender cada tipo é fundamental para otimizar workloads com joins frequentes.

Broadcast Hash Join
✓ Sem Shuffle
A tabela menor é enviada inteira a todos os executores e mantida em memória como hash map. Cada executor faz o join localmente, sem mover dados. Ativado automaticamente quando uma tabela < autoBroadcastJoinThreshold (padrão 10 MB). Force com F.broadcast(df) ou hint /*+ BROADCAST(t) */.
Shuffle Hash Join
Shuffle
Ambas as tabelas são shuffled pela chave de join para que linhas com a mesma chave fiquem na mesma partição. Depois, uma das partições é construída como hash map na memória. Requer que pelo menos uma das partições caiba em memória do executor.
Sort-Merge Join
Shuffle
Padrão para tabelas grandes no Spark SQL. Faz shuffle → sort por chave em ambas → merge. Mais robusto: funciona com qualquer tamanho de dados pois não exige que a partição caiba em memória. Pode ser eliminado com bucketing prévio.
Broadcast Nested Loop Join
⚠ Lento
Fallback para joins sem condição de igualdade (non-equi joins: <, >, BETWEEN). Uma tabela é broadcastada e a outra é percorrida em loop nested para cada linha. Extremamente lento em tabelas grandes — evite ou remodele a query.
Cartesian Join
⚠ Perigoso
CROSS JOIN explícito. Produto cartesiano: M × N linhas. Para duas tabelas de 1M linhas cada, o resultado tem 1 trilhão de linhas. Use apenas quando realmente necessário e com tabelas muito pequenas.
✓ Bucketing elimina shuffle em joins recorrentes Salve tabelas com .bucketBy(200, "user_id").sortBy("user_id").saveAsTable("nome"). Joins futuros entre tabelas bucketizadas com o mesmo número de buckets e chave eliminam o shuffle completamente — ideal para tabelas grandes lidas diariamente.

Cache e Persist: Comparativo de Storage Levels

Quando um DataFrame é reutilizado múltiplas vezes no mesmo job (ex: tabela base de lookup, resultado de transformação cara), cachear evita recomputação. cache() é equivalente a persist(MEMORY_AND_DISK). Atenção: cache é lazy — só materializa na primeira action após o cache.

MEMORY_ONLY
Acesso mais rápido possível

Se não cabe, recalcula (sem spill para disco). GC intenso com muitos objetos Java.
MEMORY_AND_DISK
Balanceado — nunca perde dados; spilla para disco se necessário

Disk I/O quando pressão de memória alta.
MEMORY_ONLY_SER
Menos memória que MEMORY_ONLY (dados serializados = compactos)

CPU extra para serializar/deserializar a cada acesso.
DISK_ONLY
Sem pressão de memória — útil para DataFrames muito grandes

Lento: puro I/O de disco a cada acesso. Raramente a escolha certa.
MEMORY_AND_DISK_SER
Melhor equilíbrio para produção: memória eficiente + fallback disco

CPU de serialização + eventual I/O de disco.
OFF_HEAP
Sem GC — Tungsten managed. Ideal para DataFrames grandes e estáveis

Requer spark.memory.offHeap.enabled=true e tamanho configurado.

Spark Structured Streaming

O Structured Streaming trata um stream de dados como uma tabela append-only infinita. Você escreve queries normais de DataFrame/SQL e o engine processa incrementalmente os novos dados a cada trigger, mantendo estado quando necessário. A semântica exactly-once é garantida por checkpointing + fontes com replay (Kafka) + sinks idempotentes (Delta Lake).

Trigger Modes

TriggerUso
ProcessingTime("30s")Micro-batch padrão
Once()Processa pendente e para (backfill)
AvailableNow()Como Once mas em múltiplos batches
Continuous("1s")Baixa latência (experimental)

Quando usar Streaming?

✓ Use Streaming quando: Detecção de fraude em tempo real, monitoramento de IoT/métricas, pipelines Kafka → Delta Lake com latência <1 min, alertas baseados em janelas de tempo (windowing).
✗ Prefira Batch quando: Latência de minutos/horas é aceitável, volume baixo, pipelines simples sem estado, menor complexidade operacional e custo.
# Exactly-once: checkpointing + Kafka (replay) + Delta Lake (idempotente)
stream = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "broker:9092") \
    .option("subscribe", "events-topic") \
    .load()

stream.writeStream \
    .format("delta") \
    .option("checkpointLocation", "s3://bucket/checkpoint/") \
    .trigger(processingTime="30 seconds") \
    .start("s3://bucket/delta-table/")

Tuning do Spark — Guia Completo e Estruturado

O tuning do Spark é uma disciplina iterativa: meça → identifique o gargalo → ajuste um parâmetro por vez → meça novamente. Aplicar todas as otimizações de uma vez sem entender o bottleneck real é a receita para perder tempo. O fluxo correto segue cinco fases em ordem de impacto.

1
Recursos: Executores, Cores e Memória
O maior impacto — configurar mal aqui invalida qualquer outra otimização

A fórmula base para dimensionar executores parte das características físicas do nó. Deixe sempre 1 core e ~4 GB para o sistema operacional e o YARN Node Manager. O número ideal de cores por executor é 4–5 — abaixo disso você não aproveita a localidade de dados; acima de 5 a contenção de I/O em disco e rede supera o ganho.

Fórmula de Dimensionamento

# Exemplo: nó r5.4xlarge — 16 vCPU / 128 GB RAM

# Passo 1: recursos disponíveis para YARN
cores_disponíveis  = 16 - 1 = 15
ram_disponível_gb  = 128 - 4 = 124 GB

# Passo 2: executores por nó
executor_cores     = 5
executores_por_nó  = 15 / 5 = 3

# Passo 3: memória por executor
ram_por_executor   = 124 / 3 = ~41 GB
executor.memory    = 36g   # deixe ~5 GB para overhead
memoryOverhead     = 4g    # 10–15% de executor.memory

# Passo 4: cluster de 10 nós
num_executors = (3 × 10) - 1 = 29
# -1 reservado para o Driver no cluster

Defina sempre minExecutors, maxExecutors e initialExecutors. Em EMR, prefira Managed Scaling no nível do cluster em vez de Dynamic Allocation no nível da aplicação.
2
Particionamento e Paralelismo
Dados mal distribuídos anulam qualquer quantidade de hardware

Regras de Particionamento

📏
Tamanho ideal por partição: 128 MB – 512 MB. Abaixo de 10 MB há overhead de scheduling; acima de 1 GB pressiona a memória do executor.
⚖️
Número de partições ≈ 2–4× o total de cores disponíveis. Com 100 cores, use 200–400 partições para manter todos os cores ocupados mesmo com variação de tempo por task.
🔀
spark.sql.shuffle.partitions padrão é 200 — muitas vezes errado. Para datasets pequenos use 50–100; para grandes use 500–2000. Com AQE ligado, ele se auto-ajusta.
⚡
Use coalesce() para reduzir partições sem shuffle. Use repartition() quando precisar redistribuir com balanceamento real (mais lento mas mais equilibrado).
🪣
Bucketing elimina shuffle em joins recorrentes. Pré-processe tabelas com bucketBy(N, "chave") e joins futuros na mesma chave não farão shuffle.

Diagnóstico de Particionamento no Spark UI

# Ver distribuição de partições do DataFrame
df.rdd.getNumPartitions()

# Verificar tamanho de cada partição (amostra)
df.rdd.mapPartitions(
  lambda it: [sum(1 for _ in it)]
).collect()

# Verificar paralismo default atual
spark.conf.get("spark.default.parallelism")
spark.conf.get("spark.sql.shuffle.partitions")

# Ajustar em runtime sem reiniciar
spark.conf.set("spark.sql.shuffle.partitions", "400")

# Reparticionamento estratégico por coluna
# (agrupa dados relacionados na mesma partição)
df.repartition(200, "user_id")
3
Otimização de Joins e Shuffles
Shuffles são a principal fonte de lentidão — minimize-os sempre que possível

Hierarquia de Estratégias de Join (do melhor ao pior)

🥇
Broadcast Join: sem shuffle. Use quando uma tabela cabe em memória. Força: F.broadcast(df) ou /*+ BROADCAST(t) */. Limite: spark.sql.autoBroadcastJoinThreshold (padrão 10 MB — aumente para 100 MB+).
🥈
Bucketed Sort-Merge Join: sem shuffle se ambas as tabelas estão bucketizadas com o mesmo N e chave. Investimento único na escrita, joins futuros gratuitos.
🥉
Sort-Merge Join com AQE: shuffle necessário mas AQE otimiza automaticamente o número de partições e detecta skew. Habilite sempre spark.sql.adaptive.enabled=true.
🚨
Sort-Merge Join sem AQE + skew: pior caso. Straggler tasks, horas de execução. Aplique salting manual ou habilite AQE.

Configurações de Join e Shuffle

# Aumentar threshold de broadcast
spark.sql.autoBroadcastJoinThreshold   = 104857600  # 100 MB

# AQE — sempre habilitar em Spark 3+
spark.sql.adaptive.enabled             = true
spark.sql.adaptive.skewJoin.enabled    = true
spark.sql.adaptive.coalescePartitions
  .enabled                             = true
spark.sql.adaptive.coalescePartitions
  .minPartitionSize                    = 67108864  # 64 MB mínimo

# Otimizar buffer de shuffle
spark.shuffle.file.buffer              = 1m        # padrão 32k — aumente
spark.reducer.maxSizeInFlight          = 96m       # padrão 48m
spark.shuffle.compress                 = true
spark.shuffle.spill.compress           = true

# Prefer sort-merge join (mais robusto que hash)
spark.sql.join.preferSortMergeJoin     = true
4
I/O: Leitura e Escrita Eficientes
Formato de arquivo, compressão e estratégia de escrita impactam I/O em 5–10×

Leitura Otimizada do S3

📂
Use Parquet + Snappy/Zstd. Parquet com predicate pushdown e column pruning reduz I/O em 80–95% vs CSV. Zstd oferece melhor compressão que Snappy com custo de CPU similar.
🗂️
Particionamento por colunas de filtro frequente. partitionBy("year","month","day") — filtros nessas colunas eliminam prefixos S3 inteiros sem ler nada.
📊
Tamanho ideal de arquivo: 256 MB – 1 GB. Arquivos menores geram overhead de S3 LIST; maiores dificultam paralelismo. Ajuste spark.sql.files.maxPartitionBytes.
🔍
S3 Select / Iceberg data skipping. S3 Select filtra CSV/JSON no lado do S3 antes de enviar à rede. Iceberg usa min/max statistics por arquivo para pular arquivos inteiros sem lê-los.

Escrita Otimizada no S3

# Evitar small files ao escrever
df.coalesce(50)  # sem shuffle — reduz partições
  .write
  .mode("overwrite")
  .parquet("s3://bucket/tabela/")

# Escrita particionada com overwrite dinâmico
spark.conf.set(
  "spark.sql.sources.partitionOverwriteMode",
  "dynamic"  # sobrescreve só as partições afetadas
)
df.write.mode("overwrite")
  .partitionBy("year", "month")
  .parquet("s3://bucket/tabela/")

# Compressão recomendada
spark.sql.parquet.compression.codec = zstd

# Tamanho de partição de saída

Código: APIs, UDFs e Serialização
Código mal escrito desperdiça recursos que hardware extra não resolve

Boas Práticas de Código Spark

⚡
Prefira funções nativas do pyspark.sql.functions. São compiladas via Catalyst/Tungsten — 10–100× mais rápidas que Python UDFs row-by-row que quebram o Tungsten pipeline.
🐼
Use Pandas UDFs (vectorized) se precisar de lógica customizada. Operam sobre Arrow batches em vez de row-by-row. Tipos: SCALAR, GROUPED_MAP, GROUPED_AGG. Mais rápidos que UDFs escalares Python.
💾
Cache seletivo: use df.cache() ou df.persist() apenas em DataFrames reutilizados 2+ vezes no mesmo job. Cachear tudo consome memória que seria usada para execução.
🔗
Evite acumulação de transformações sem checkpoint em streaming. Em jobs longos com muitas transformações encadeadas, o lineage cresce indefinidamente. Use df.checkpoint() a cada N iterações para quebrar o lineage.
🚫
Nunca use .collect() em dados grandes. Traz tudo para o Driver — único ponto de falha. Use .write() para persistir, .limit(N).collect() para inspeção, ou .take(N) para amostras.

Comparativo: Python UDF vs Pandas UDF vs Nativa

# ❌ EVITE: Python UDF escalar — row-by-row, lento
from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

slow_udf = udf(lambda x: x.upper() if x else "", StringType())
df = df.withColumn("upper", slow_udf("nome"))

# ✅ PREFIRA: função nativa do Spark
import pyspark.sql.functions as F
df = df.withColumn("upper", F.upper("nome"))

# ✅ SE PRECISAR DE LÓGICA CUSTOM: Pandas UDF
from pyspark.sql.functions import pandas_udf
import pandas as pd

@pandas_udf(StringType())
def minha_logica(s: pd.Series) -> pd.Series:
    return s.str.upper().str.strip()

df = df.withColumn("upper", minha_logica("nome"))

Debugging no Spark — Spark UI, Logs e Metodologia

Debugging eficaz no Spark segue uma metodologia top-down: comece pelo panorama geral (job completo), desça para stages, depois tasks individuais, e só então inspecione logs de container. Pular etapas é a principal causa de debugging demorado.

Metodologia de Debugging — Passo a Passo

01
Spark UI → Jobs tab: identifique o job mais lento

Acesse http://<driver>:4040 (ativo) ou Spark History Server (concluído). Na aba Jobs, identifique jobs com duração anormal. Clique no job para ver os stages.

02
Stages tab: localize o stage gargalo

Stages com shuffle read/write alto são candidatos a skew ou join ineficiente. Stages com muitas tasks em FAILED indicam OOM ou erros de serialização. Anote o Stage ID problemático.

03
Stage Details → Task Metrics: analise a distribuição

Ordene tasks por Duration. Se a distribuição for bimodal (maioria rápida, algumas lentas), é skew. Verifique Shuffle Read Size — tasks lentas com 10× mais dados confirmam data skew. Verifique GC Time — se >10% é problema de memória.

04
SQL tab → Plano físico: verifique o plano de execução

Clique em uma query SQL para ver o DAG visual e o plano físico. Verifique: PartitionFilters (predicate pushdown ativo), tipo de join (BroadcastHashJoin ou SortMergeJoin), e se há Exchange (shuffle) desnecessários. Um BroadcastHashJoin é sempre melhor que SortMergeJoin quando possível.

05
Executors tab: verifique saúde dos executores

Coluna GC Time: se >10% do task time, problema de memória. Coluna Failed Tasks: executores com muitas falhas indicam instabilidade (Spot, OOM). Coluna Shuffle Read/Write: desequilíbrio entre executores sugere skew ou dados não-distribuídos uniformemente.

06
Environment tab: confirme configurações ativas

Verifique se spark.sql.adaptive.enabled está true, quais JARs foram carregados, versão do Spark, e variáveis de ambiente. Erros de classpath e dependências aparecem aqui.

07
Container logs: investigue erros específicos

No EMR: CloudWatch Logs → /aws/elasticmapreduce/<cluster-id> → containers → stderr do container YARN. No Spark Standalone: $SPARK_HOME/logs/. Busque por ERROR, Exception, OutOfMemory. O erro real geralmente está no stderr do container, não no stderr da aplicação.

Erros Comuns no Spark e Como Resolvê-los

OOM · Executor
java.lang.OutOfMemoryError: Java heap space
Causa: DataFrame muito grande para a heap do executor, UDFs acumulando objetos ou collect() trazendo dados demais ao Driver.

Fix: Aumente spark.executor.memory. Reduza spark.executor.cores para dividir menos a memória. Aumente partições para processar chunks menores. Substitua UDFs Python por funções nativas do pyspark.sql.functions.
OOM · YARN
Container killed by YARN for exceeding memory limits
Causa: Processo executor excedeu o limite YARN. Comum com PySpark (processo Python separado), Arrow/Pandas UDFs ou bibliotecas nativas.

Fix: Aumente spark.executor.memoryOverhead (mínimo 384 MB, ideal 15–20% da executor.memory). Para PySpark com Pandas, ajuste também spark.executor.pyspark.memory.
Performance
Job extremamente lento — straggler tasks
Causa: Data skew — algumas partições concentram muito mais dados. No Spark UI: Stage Details → Task Duration, se P99 for 10× a mediana é skew.

Fix: Ative AQE com spark.sql.adaptive.skewJoin.enabled=true. Para skew severo aplique salting manual. Para joins, use broadcast se a menor tabela couber em memória.
Performance
Too many small files — leitura muito lenta
Causa: Milhares de arquivos <10 MB no S3 causam overhead de LIST e OPEN requests antes de qualquer processamento real. Comum após writes com muitas partições.

Fix: Use coalesce(N) ou repartition(N) antes de escrever. Use compaction do Iceberg/Delta/Hudi. Ajuste spark.sql.files.maxPartitionBytes=268435456.
Serialização
SparkException: Task not serializable
Causa: Um objeto não-serializável (conexão de banco, sessão HTTP, logger) está sendo capturado em uma closure de transformação Spark — o Driver tenta enviá-lo ao executor e falha.

Fix: Inicialize o objeto dentro da função (não fora no Driver). Use foreachPartition para abrir conexões uma vez por partição.
Shuffle
FetchFailedException — shuffle data lost
Causa: Executor morreu durante o shuffle (instância Spot interrompida ou OOM) e os dados do shuffle map foram perdidos. O reducer não consegue buscar os dados.

Fix: Ative External Shuffle Service: spark.shuffle.service.enabled=true. Não use Spot em Core nodes. Aumente spark.task.maxFailures=8 para retries.
Schema
AnalysisException: cannot resolve column
Causa: Nome de coluna incorreto, coluna removida em operação anterior, ou ambiguidade em joins — mesma coluna em ambas as tabelas sem alias.

Fix: Use aliases: df_a["col"] vs df_b["col"]. Renomeie com .withColumnRenamed() antes do join. Imprima df.printSchema() para inspecionar o schema atual.
Streaming
StreamingQueryException: checkpoint incompatível
Causa: Schema da query ou operadores mudaram após o checkpoint ser criado — Spark não consegue recuperar o estado com a nova lógica.

Fix: Delete o checkpoint e reinicie do zero aceitando a perda de estado parcial. Em produção, versione checkpoints por deploy: s3://bucket/checkpoint/v3/.
Conectividade
Executor heartbeat timed out
Causa: GC longo pausa o executor além do timeout de heartbeat. O Driver marca o executor como morto e resubmete todas as tasks — criando ciclo de falhas.

Fix: Aumente spark.network.timeout=600s e spark.executor.heartbeatInterval=60s. A raiz sempre é GC/memória — resolva primeiro com mais memória ou G1GC.
Leitura S3
Job lento ao ler Parquet — full scan desnecessário
Causa: Tabela não está particionada pela coluna de filtro, ou o predicate pushdown não está funcionando. O Spark lê todos os arquivos mesmo com filtro aplicado.

Fix: Particione a tabela por colunas usadas em filtros frequentes (ex: partitionBy("year","month")). Verifique no Spark UI → SQL → plan físico se aparece "PartitionFilters". Use Iceberg/Delta para partition evolution sem rewrite.

Conceitos Fundamentais do AWS EMR

O Amazon EMR (Elastic MapReduce) é o serviço gerenciado da AWS para processamento distribuído em larga escala. Entender seus componentes e modelos de implantação é essencial para projetar clusters eficientes e econômicos.

Implantação
Clusters Transientes vs Persistentes
Transiente: criado para um job e terminado ao fim. Ideal para batch com S3. Custo menor. Persistente: cluster contínuo para workloads interativas (notebooks, Hive). Custo maior. Para a maioria dos casos, prefira clusters transientes com EMRFS.
Gerenciamento
Instance Groups vs Instance Fleets
Instance Groups: define um tipo fixo por grupo. Simples mas inflexível para Spot. Instance Fleets: define múltiplos tipos por grupo — EMR escolhe os disponíveis automaticamente. Reduz interrupções Spot e maximiza economia. Use sempre Fleets para Task nodes em produção.
Escala
Managed Scaling
Monitora métricas YARN em tempo real (YARNMemoryAvailablePercentage, ContainerPendingRatio) e adiciona/remove nós Task automaticamente. Para pipelines com demanda variável, pode reduzir custo em 40–60% vs cluster fixo. Reage em aprox. 2–5 minutos.
Storage
EMRFS — S3 como Filesystem
EMRFS usa o S3 diretamente como filesystem, substituindo o HDFS local. Dados persistem após término do cluster, múltiplos clusters compartilham os mesmos dados, sem custo de replicação HDFS. O S3 hoje é fortemente consistente — EMRFS Consistent View via DynamoDB não é mais necessário.
Execução
Steps e Modos de Submissão
Jobs no EMR são submetidos como Steps: cada step é um comando Spark, Hive ou script. Modos: (1) EMR Steps API, (2) Livy REST API, (3) EMR Studio notebooks, (4) spark-submit via SSH. Para automação, prefira Steps API com Step Concurrency Level para paralelismo.
Custo
Spot Instances no EMR
Task nodes não armazenam HDFS — seguros para Spot. Com Instance Fleets diversificando 5–8 tipos, probabilidade de interrupção total é <5%. Economia típica: 60–80% vs On-Demand. Core e Master: sempre On-Demand.
Serverless
EMR Serverless
Submeta jobs Spark/Hive sem provisionar clusters. AWS provisiona workers sob demanda; você paga por segundo. Cold start: aprox. 20–40s. Ideal para pipelines não-críticos em latência. Limitação: menos controle de JVM, sem acesso SSH, sem Spot.
Kubernetes
EMR on EKS
Permite submeter jobs Spark ao EKS (Kubernetes) via EMR. Benefícios: compartilhamento de cluster K8s, isolamento por namespace, integração com Karpenter para auto-scaling. Ideal para equipes que já operam EKS.

Job falha no commit — arquivos _temporary não removidos
Causa: O committer padrão do Spark cria diretórios _temporary no S3 e faz rename atômico. O S3 não suporta rename real — é copy+delete. Em jobs grandes isso causa timeout ou S3 throttling.

Causa: O Instance Profile do EMR não tem permissão na bucket de destino, ou a bucket tem política de negação explícita. Comum ao cruzar contas AWS.

HDFS · Core Node
HDFS NameNode em Safe Mode
Causa: Após falha de um Core node, o NameNode entra em Safe Mode e recusa escritas até ter quórum de blocos replicados. Ocorre em arquiteturas que ainda usam HDFS.

Fix: hdfs dfsadmin -safemode leave para sair forçadamente. Prefira EMRFS (S3) como storage principal — elimina completamente a dependência de HDFS e o risco de Safe Mode.
Logs · Debugging
Erro na aplicação sem mensagem clara no console
Causa: O erro real está nos logs do container YARN, não no Step output visível no console EMR.

Fix: Acesse: CloudWatch Logs → /aws/elasticmapreduce/<cluster-id> → containers → stderr do container da aplicação. Ou habilite Log URI no cluster para arquivar em S3 e inspecionar com S3 Select ou Athena.
Performance · I/O
Job lento — S3 throttling (SlowDown errors)
Causa: Muitos executores fazendo requests simultâneas ao mesmo prefixo S3 ultrapassam o limite de 3.500 PUT/s ou 5.500 GET/s por prefixo.

id="s3-iceberg">Apache Iceberg — Table Format para Data Lakehouse

O Apache Iceberg é um formato de tabela aberto para grandes conjuntos de dados analíticos no data lake. Resolve os problemas críticos do Hive (sem ACID, particionamento inflexível, sem time travel) adicionando uma camada de metadados sofisticada sobre arquivos Parquet/ORC no S3 — sem precisar de um banco de dados central.

Core Feature
ACID Transactions
Iceberg garante atomicidade em escritas concorrentes usando Optimistic Concurrency Control. Múltiplos writers podem operar simultaneamente; em conflito, o segundo commit falha e deve ser retentado. Sem corrupção de dados mesmo com falha no meio de um write.
Core Feature
Time Travel & Snapshots
Cada write cria um snapshot imutável. Consulte versões anteriores:
SELECT * FROM tabela VERSION AS OF 12345
SELECT * FROM tabela TIMESTAMP AS OF '2024-01-01'
Rollback de produção em segundos. Auditoria completa de mudanças.
Core Feature
Schema Evolution
Adicione, renomeie, reordene ou remova colunas sem reescrever dados históricos. Iceberg rastreia a evolução do schema por coluna ID — arquivos antigos continuam legíveis mesmo após mudanças. Suporta ADD COLUMN, RENAME COLUMN, DROP COLUMN, RENAME PARTITION.
Core Feature
Partition Evolution
Mude a estratégia de particionamento sem reescrever dados existentes. Ex: migre de particionamento mensal para diário aplicando a nova estratégia apenas aos dados novos. Queries continuam corretas e eficientes em ambas as partições.
Performance
Hidden Partitioning
Iceberg aplica transformações de particionamento automaticamente — users não precisam incluir filtros de partição nas queries. WHERE event_time > '2024-01-01' automaticamente poda as partições corretas sem WHERE year=2024 AND month=1. Elimina erros de partição.
Performance
Metadata Statistics
Manifests armazenam estatísticas por arquivo: min/max de colunas, contagem de nulos, contagem de linhas. O Iceberg elimina a leitura de arquivos inteiros com base nestas estatísticas — data skipping automático sem precisar de índices separados.
DML
Upserts (MERGE INTO)
Suporte nativo a MERGE INTO, UPDATE e DELETE com semântica SQL padrão. Internamente usa Copy-on-Write (COW) ou Merge-on-Read (MOR): COW reescreve arquivos afetados; MOR escreve delete files e merge na leitura — tradeoff write vs read performance.
Manutenção
Compaction & Cleanup
Snapshots antigos e arquivos pequenos precisam de manutenção periódica:
CALL system.rewrite_data_files('db.tabela') — compacta arquivos pequenos.
CALL system.expire_snapshots(...) — remove snapshots antigos.
CALL system.remove_orphan_files(...) — limpa arquivos órfãos.

✓ Quando escolher Iceberg no seu data lake? Use Iceberg quando precisar de: (1) MERGE/UPDATE/DELETE frequentes em grandes tabelas, (2) múltiplos engines consultando os mesmos dados (Spark + Athena + Trino), (3) evolução de schema e particionamento sem downtime, ou (4) auditoria e rollback via time travel. Erros Comuns em Arquitetura de Dados e Como Resolvê-los

Data Lake · Qualidade
Data Swamp — lake virou pântano de dados
Causa: Dados chegam sem schema, sem catalogação, sem linhagem. Ninguém sabe o que existe, quem criou, quando foi atualizado ou se é confiável. Comum em projetos sem governança desde o início.

Fix: Implante Glue Crawlers + Data Catalog. Use AWS Lake Formation para controle de acesso e linhagem. Adicione Great Expectations para validação de qualidade. Crie convenções de nomenclatura e ownership de datasets.
Formato · Parquet
Small files problem — milhares de Parquets minúsculos
Causa: Streaming que escreve frequentemente, writes com muitas partições Hive, ou jobs sem coalesce. Resulta em listagens S3 lentas e leituras ineficientes.

Fix: Use compaction automática do Iceberg/Delta/Hudi. Para Parquet puro, crie um job de compaction periódico com Spark: leia todos os arquivos de uma partição e reescreva como arquivo único de 256–512 MB.
Governança · Acesso
PII exposto em dados brutos
Causa: Dados com CPF, email, cartão foram ingeridos sem mascaramento na camada Raw. Com acesso amplo ao S3, qualquer analista pode ver dados sensíveis.

Fix: Use Amazon Macie para detectar PII automaticamente. Implante Lake Formation column-level security. Mascare na camada Silver com hashing ou tokenização. Revise permissões do bucket Raw para acesso mínimo.
Pipeline · Idempotência
Dados duplicados após reprocessamento
Causa: Pipeline não é idempotente — ao reprocessar um intervalo de tempo por falha, os dados são inseridos novamente gerando duplicatas na tabela destino.

Fix: Use MERGE INTO (Iceberg/Delta) em vez de INSERT. Mantenha um campo de watermark ou job_run_id. Para Parquet puro, sobrescreva a partição inteira (não faça append): .mode("overwrite").option("partitionOverwriteMode","dynamic").
Custo · S3
Custo de S3 explodindo inesperadamente
Causa: Buckets sem lifecycle policy acumulam versões antigas, arquivos temporários não deletados, snapshots Iceberg/Delta nunca expirados, ou tiers de storage incorretos.

Fix: Configure S3 Lifecycle Policies (mover para Glacier após 90 dias, deletar versões antigas após 30 dias). Execute expire_snapshots regularmente em tabelas Iceberg. Habilite S3 Intelligent-Tiering para dados com padrão de acesso variável.
Observabilidade
Pipeline falhou silenciosamente — ninguém percebeu
Causa: Jobs sem alertas configurados. O pipeline de relatórios diários falhou às 2h da manhã e a equipe só descobriu quando o usuário reclamou às 9h que os dados estavam desatualizados.

Fix: Configure CloudWatch Alarms para cada Step Functions state machine. Use EventBridge para capturar falhas de Glue/EMR e notificar via SNS/Slack. Implante data freshness checks: alerte se a tabela não foi atualizada no SLA esperado.

Erros Comuns em Extração & Persistência e Como Resolvê-los

DynamoDB · Leitura
Scan completo em tabela de produção causa throttling
Causa: Job Spark usando conector DynamoDB faz Full Scan consumindo toda a capacidade de leitura (RCU) da tabela, causando ProvisionedThroughputExceededException em produção.

Fix: Nunca use Scan em produção. Use DynamoDB Export to S3 (snapshot completo sem impacto). Para CDC incremental, use DynamoDB Streams + Kinesis Firehose. Se precisar de Scan, use uma réplica global ou agende para horário de baixo tráfego com ReturnConsumedCapacity.
RDS · JDBC
JDBC connection timeout — extração trava
Causa: Query JDBC sem particionamento cria uma única conexão e tenta trazer todos os dados de uma vez. Com tabelas grandes, o timeout da conexão é atingido antes de concluir.

Fix: Use particionamento JDBC no Spark: .option("partitionColumn","id").option("lowerBound",0).option("upperBound",max_id).option("numPartitions",50). Cada partição abre uma conexão paralela. Ajuste o pool de conexões do RDS (max_connections) para acomodar.
S3 · Escrita
Escrita S3 lenta — commit demora mais que o job
Causa: Committer padrão do Spark cria milhares de arquivos em _temporary e depois faz rename sequencial. S3 não tem rename real — é copy+delete, O(n) em número de arquivos.

Fix: Use o S3A Committer (spark.hadoop.mapreduce.outputcommitter.factory.scheme.s3a=org.apache.hadoop.fs.s3a.commit.S3ACommitterFactory) ou o EMR optimized committer. Ambos usam multipart upload direto, eliminando o _temporary.
Redshift · COPY
COPY command falha ou é muito lento
Causa: Arquivo de origem em formato não ideal (CSV sem compressão), número de arquivos não alinhado com slices do cluster, ou permissões IAM insuficientes.

Fix: Prefira Parquet comprimido — COPY de Parquet é 2–3× mais rápido. Gere 1 arquivo por slice do Redshift (ex: 16 slices = 16 arquivos). Configure o IAM role com acesso ao bucket S3 e passe no COPY: COPY tabela FROM 's3://...' IAM_ROLE 'arn:...'.
DMS · CDC
DMS atrasando — replication lag crescendo
Causa: Instância de replicação DMS subdimensionada, workload de escrita alto na fonte, ou LOBs (Large Objects) lentos para replicar. Replication lag indica que o CDC está ficando para trás.

Fix: Aumente a classe da instância DMS (r5.2xlarge para cargas altas). Ative BatchApplyEnabled=true para aplicar mudanças em lotes. Para LOBs, considere limited LOB mode. Monitore CloudWatch: CDCLatencySource e CDCLatencyTarget.
Schema · Evolução
Pipeline quebra após ALTER TABLE na fonte
Causa: A fonte (RDS/Aurora) teve uma coluna adicionada ou renomeada. O job Spark com schema hardcoded falha com AnalysisException ou silenciosamente ignora a nova coluna.

Fix: Nunca use schema hardcoded em extração. Use spark.read.jdbc(...).option("inferSchema","true") ou mantenha schema registry (Glue Schema Registry, Confluent). Use Iceberg na destino para absorver schema evolution sem reprocessar dados históricos.

Erros Comuns em Arquiteturas GenAI e Como Resolvê-los

RAG · Qualidade
Respostas imprecisas — RAG recupera contexto irrelevante
Causa: Chunking inadequado (chunks muito grandes ou muito pequenos), modelo de embedding não alinhado ao domínio, ou k muito baixo na busca vetorial.

Fix: Experimente chunk sizes de 256–1024 tokens com overlap de 20%. Aumente k na busca vetorial (top-10 ao invés de top-3). Use re-ranking (cross-encoder) para refinar os resultados antes de injetar no prompt. Avalie com métricas RAGAS (faithfulness, context precision).
Segurança · PII
Dados sensíveis expostos via LLM
Causa: Pipeline de embeddings indexou documentos com CPF, dados bancários ou PHI sem mascaramento. O LLM recupera e expõe esses dados nas respostas.

Fix: Execute Macie scan antes de qualquer ingestão no vector store. Use presidio ou AWS Comprehend para detectar e mascarar PII nos chunks antes de embeddar. Configure Bedrock Guardrails para bloquear saídas com padrões de PII.
Custo · API
Custo de API LLM explodindo
Causa: Prompts muito longos (contexto RAG desnecessariamente grande), sem cache de respostas repetidas, ou chamadas sem necessidade para perguntas que não precisam de LLM.

Fix: Implante prompt cache (Bedrock Prompt Caching). Limite o contexto RAG ao mínimo necessário (top-3 chunks relevantes). Use modelos menores (Haiku, Titan Lite) para tasks simples. Adicione filtro pré-LLM: perguntas FAQ respondem com cache sem chamar o modelo.
Fine-tuning · Dados
Modelo fine-tunado pior que o base
Causa: Dataset de fine-tuning com dados de baixa qualidade, contaminados ou com viés. Quantidade insuficiente de exemplos para o domínio. Formato de instrução incorreto.

Fix: Qualidade supera quantidade — 1.000 exemplos perfeitos > 50.000 ruidosos. Revise manualmente uma amostra aleatória. Use o formato correto de instrução do modelo base (alpaca, chatml, etc). Avalie com holdout set antes de deployar.
Vector Store · Escala
Busca vetorial lenta com base crescendo
Causa: Índice vetorial sem configuração de HNSW/IVF adequada, ou vector store sem sharding para bases acima de 10M vetores. A busca ANN degrada linearmente sem índice correto.

Fix: Configure HNSW com efConstruction=200 e M=16 para melhor tradeoff precision/speed. Para OpenSearch, use engine FAISS com IVF para bases grandes. Considere namespaces/shards por tenant em arquiteturas multi-tenant.
Alucinação · Confiança
LLM inventa informações não presentes no contexto
Causa: Prompt sem instrução explícita de grounding, temperatura muito alta, ou contexto RAG insuficiente forçando o modelo a completar com conhecimento paramétrico incorreto.

Fix: Adicione ao system prompt: "Responda APENAS com base no contexto fornecido. Se a informação não estiver no contexto, diga que não sabe." Reduza temperature para 0.1–0.3 em tasks factuais. Implante faithfulness check pós-geração com um segundo LLM verificador.
